# 07. The interface layer: one fast CU engine, every model and harness

Research date: 2026-10-11. Sources were checked on that date. Anything I could not confirm against a primary source is marked **unverified**. Model names in this note (Claude Opus 5.5, GPT-6.1 Sol, GPT-6 Astra, Gemini 3.8 Flash and so on) are the ones the vendors' docs use today.

## TL;DR

- **Every lab now ships a different, versioned CU tool, and they disagree on almost everything.** Anthropic moved to `computer_toolset_20260801` in August 2026: 17 member tools, batched calls, zoom on by default, no display size, screenshot-pixel coordinates. OpenAI GA'd a bare `{type:"computer"}` tool with an `actions[]` batch, and now recommends code execution over that tool for GPT-6 Astra. Gemini's `computer_use` emits normalized 0-999 coordinates. Qwen3-VL uses an Anthropic-like action list with 0-1000 coordinates. UI-TARS emits its own text grammar.
- **The labs' own desktop CU products already run over MCP.** Codex CU is the `cua_repl` MCP server. Claude Code's built-in computer use is an MCP server called `computer-use`. cua's benchmark runs Codex CU under Claude Code over MCP as a first-class setup. MCP is the right default front end.
- **Code mode is where the momentum is.** OpenAI recommends code execution for its newest CU model. Codex, Pi 1.0 and Cloudflare ship JS code modes. Anthropic reports +11% accuracy with 24% fewer input tokens from programmatic tool calling on search tasks. CodeAct (ICML 2024) reports up to 20% higher success over JSON actions. The catch is that model-written code must run in a capability sandbox. OpenAI says to enforce permissions "in the exposed helpers and runtime", since one script can perform many actions.
- **Images reach the model in most harnesses, with caveats that matter for clicking.** Claude Code, Codex, Cursor, VS Code, Gemini CLI, Zed, Goose and Pi all forward MCP image content. OpenCode moves images into a synthetic user message with no call attribution. ChatGPT is inconsistent. Harnesses and APIs may silently downscale images, which breaks pixel coordinates unless the server pre-sizes screenshots.
- **Pre-size screenshots to a "no-rescale box".** A frame with `ceil(w/28) * ceil(h/28) <= 1568` and a long edge under 1568 px is never resized by any Claude model. It matches the size Claude Code's own CU sends for a Retina MacBook capture, about 1372x887. The same frame costs about 1.2k to 1.6k tokens on OpenAI with `detail:"original"`. Gemini charges a flat 1120 or 2240 tokens and works in normalized space, so size matters less there.
- **Elicitation-based approvals are not portable.** Claude Code, Codex, Cursor and VS Code support elicitation. Gemini CLI, Zed and Pi do not. OpenCode and Claude Desktop/Cowork declare it but drop or hang on requests. Treat elicitation as a nice UI path, and own an out-of-band approval channel in the engine.
- **MCP 2026-07-28 changed the ground under us.** The core is stateless (no `initialize`, no sessions). Elicitation now arrives as an `input_required` result on retry (MRTR). Tasks moved to an extension. Sampling and roots are deprecated. A server must speak both the legacy and modern eras. cua-driver already does this over stdio.
- **Recommended shape: one engine, three faces.** (1) An MCP server with a code profile (`js`, `js_reset`, Codex-compatible) and a small fine-grained tool profile for weaker coders and code-mode harnesses. (2) Thin provider-native adapters for direct API use (Anthropic toolset, OpenAI `computer` and `exec_js`, Gemini `computer_use`, Qwen `computer_use`, UI-TARS grammar). (3) One frame/coordinate/image layer that every face uses. Element-index targeting from the accessibility tree is the main tool for model-agnostic accuracy. Pixels are the fallback.

## Detailed findings

### 1. Provider-native CU tools

#### Anthropic

- The current tool is `computer_toolset_20260801`. It is GA with no beta header on the Claude API and Google Cloud. Supported models are Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 5, Sonnet 5.5, Sonnet 5, Opus 4.8 and Haiku 5.5. Bedrock, Foundry and Claude Platform on AWS only offer the earlier beta tools ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)).
- Claude 5.5 models on the Claude API and Google Cloud reject `computer_20251124` and `computer_20250124` with a 400. On Bedrock they still accept `computer_20251124`. Opus 4.7, Opus 4.6, Sonnet 4.6 and Opus 4.5 only support `computer_20251124` with a beta header ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool), [release notes](https://platform.claude.com/docs/en/release-notes/overview)).
- The toolset takes no display size. "Coordinates are always in the pixel space of the screenshots you return." After a `zoom`, coordinates stay in the full screenshot's space ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)).
- Batch actions: Claude can return click, type, screenshot in one response. The client must run them in order, stop at the first failure, and answer every later block with `is_error:true` and the exact text "Not executed: an earlier computer action in this turn failed." Leaving any block unanswered is a 400. If a batch does not end with a screenshot, the client may attach one to the last result to save a round trip. Human confirmation must happen "before each block runs, because a batch can complete a multistep action within one turn" ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)).
- Launch claim, from a customer quote: a claims workflow went from 32 to 13 minutes and cost per task fell about 30% with batch actions ([Claude blog, 2026-08-20](https://claude.com/blog/computer-use-skills-api-files-api)). This is a single customer anecdote, not a benchmark.
- Recommended resolutions: 1024x768 or 1280x720 for desktop, 1280x800 or 1366x768 for web apps, avoid above 1920x1080. Screenshots cost "roughly 1,000-1,800 input tokens each" ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)).
- macOS Retina captures at 2x, so downscale by 2 or halve Claude's coordinates (same source).
- The toolset's `allowed_callers` accepts only `"direct"`, so Claude cannot call it from Anthropic's server-side programmatic tool calling. Programmatic tool results must also be text only; "Image, document, and other content block types are rejected" ([programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Anthropic's server-side code mode cannot see screenshots, so any CU code mode has to live on the client side.
- The Python and TypeScript SDKs gained beta classes for the computer and browser toolsets on 2026-10-07. You subclass one, write one method per tool, and the SDK runs the loop and an approval callback ([release notes](https://platform.claude.com/docs/en/release-notes/overview)). This is useful prior art for our Anthropic adapter.
- A separate `browser_toolset_20260801` exists for browser viewports with accessibility-tree element references ([release notes](https://platform.claude.com/docs/en/release-notes/overview)). Anthropic itself splits "desktop pixels" from "browser elements".

#### OpenAI

- The GA tool is `{ type: "computer" }` on the Responses API. A `computer_call` carries an ordered `actions[]` array. Supported actions are `click`, `double_click`, `drag`, `move`, `scroll`, `keypress`, `type`, `wait`, `screenshot`. Results go back as `computer_call_output` with `{type:"computer_screenshot", image_url, detail:"original"}` ([computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use), [integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)).
- Field details from the action handlers: `click` has `x`, `y`, `button`, optional `keys`; `drag` has a `path` of at least two points; `scroll` has `x`, `y`, `scroll_x`, `scroll_y`; `keypress` has `keys[]`. Modifier `keys` on mouse actions are held for the duration of the action ([integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)).
- Migration from the preview: model `computer-use-preview` became `gpt-6.1-sol`, `computer_use_preview` became `computer`, one `action` became an `actions[]` batch, and `truncation:"auto"` is no longer needed. The preview took `display_width`, `display_height` and `environment` (same source).
- "For GPT-6 Astra, we recommend code execution. The `computer` tool remains supported as an alternative." Code execution is an ordinary function tool that takes a script; outputs return as text and images; "Keep the environment available between calls" ([computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use)). This is close to Codex CU's `js` design.
- "The model does not need the built-in `computer` tool to call a function that operates a browser or a desktop." Function outputs can include text and images. OpenAI suggests comparing designs "on task success, time to completion, number of model turns, recovery from unexpected UI state, and adherence to your permission rules" ([integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)). That is a good eval rubric for us.
- Resolution: "strong performance with 1440 x 900 and 1600 x 900", and "Avoid using `high` or `low` image detail for computer use tasks" (same source).
- Third-party OpenAI-compatible gateways often reject or drop `input_image` inside `function_call_output`; the usual fix is a text output followed by a user message with the image ([pi #9518](https://github.com/earendil-works/pi/issues/9518), [ai-dynamo #210](https://github.com/ai-dynamo/frontend-crates/issues/210)).

#### Google

- `computer_use` runs on the Interactions API with `environment` set to `browser`, `desktop` or `mobile`. Models: `gemini-3.8-flash` (recommended), `gemini-3.5-flash-lite`, `gemini-3-flash-preview`. Still labeled Preview ([Gemini computer use](https://ai.google.dev/gemini-api/docs/computer-use)).
- Every predefined function carries an `intent` string. Coordinates are `int (0-999)`, converted with `int(x / 1000 * screen_width)`. "There is no need to specify the display size" (same source).
- Desktop has the browser set minus `navigate`, `go_back`, `go_forward`. You can exclude predefined functions and add your own, for example a `yield_to_user` function for human handoff (same source).
- Function results carry a text part and an image part, `{"type":"image","data":..., "mime_type":"image/png"}`. Every parallel call needs its own `function_result` (same source). Gemini 3 also accepts images in ordinary function results ([function calling](https://ai.google.dev/gemini-api/docs/function-calling)).
- Safety: a `safety_decision` with `require_confirmation` must be acknowledged with `safety_acknowledgement` after the user confirms. Policies include `FINANCIAL_TRANSACTIONS`, `SENSITIVE_DATA_MODIFICATION`, `COMMUNICATION_TOOL`, `ACCOUNT_CREATION`, `DATA_MODIFICATION`, `USER_CONSENT_MANAGEMENT`, `LEGAL_TERMS_AND_AGREEMENTS`. Disabling policies is a preference only; "always implement safety decision handling" ([Gemini computer use](https://ai.google.dev/gemini-api/docs/computer-use)).
- Direct API adapters must keep Gemini 3 thought signatures on function calls, or the next request fails with a 400 ([mermaid-cli PR #509](https://github.com/noahsabaj/mermaid-cli/pull/509)).

#### Open-weight models

- Qwen3-VL's cookbook registers `computer_use` and `mobile_use` tools. The `computer_use` enum is `key`, `type`, `mouse_move`, `left_click`, `left_click_drag`, `right_click`, `middle_click`, `double_click`, `triple_click`, `scroll`, `hscroll`, `wait`, `terminate`, `answer` ([agent_function_call.py](https://github.com/QwenLM/Qwen3-VL/blob/main/cookbooks/utils/agent_function_call.py)). These are nearly Anthropic's 2025 action names. cua's Qwen 3.5 loop rescales from 0-1000 ([cua qwen35.py](https://github.com/trycua/cua/blob/main/libs/python/agent/cua_agent/loops/qwen35.py)). Users report the cookbooks disagree on 999 versus 1000 and on smart-resize ([Qwen3-VL #1640](https://github.com/QwenLM/Qwen3-VL/issues/1640), [#1521](https://github.com/QwenLM/Qwen3-VL/issues/1521)).
- UI-TARS uses a text grammar. The current `prompt.py` uses `click(point='<point>x1 y1</point>')`; older builds use `start_box`. The `ui-tars` package parses output into pyautogui code ([UI-TARS prompt.py](https://github.com/bytedance/UI-TARS/blob/main/codes/ui_tars/prompt.py), [README_v1](https://github.com/bytedance/UI-TARS/blob/main/README_v1.md)). I did not find a separate UI-TARS-2 template (**unverified** whether it differs).
- GLM-V grounding returns 0-1000 boxes inside `<|begin_of_box|>` tokens, with GUI prompts per model version ([GLM-V](https://github.com/zai-org/GLM-V)). Open-AutoGLM uses 0-999 points and a `Take_over` action ([Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM/blob/main/README_en.md)). GLM-5V-Turbo is closed and I found no published action schema.
- Qwen-UI-Agent (July 2026 report) mixes GUI actions with `cli_command`, `api_call` and `ask_user`, and batches compatible actions. CLI commands were 40.7% to 55.1% of actions on OSWorld variants. Weights were not public as of late August 2026 ([Qwen-UI-Agent report](https://arxiv.org/html/2607.28227v1); availability from secondary sources, **unverified** today). Qwen3.8-27B reportedly scores 84.3 on OSWorld-Verified (secondary sources only, **unverified**).

#### Which models expect their own tool

- Native tools are trained interfaces. Anthropic injects a computer-use system prompt when the tool is declared ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Gemini and Qwen models think in normalized space. UI-TARS and GLM expect their own templates.
- Practitioners move models onto their native tool when they can. Stagehand merged "Gemini native computer use" on 2026-10-04, and mermaid-cli gave Gemini "the `computer_use` tool they are trained on" instead of a generic `computer` schema ([stagehand #2906](https://github.com/browserbase/stagehand/pull/2906), [mermaid-cli #509](https://github.com/noahsabaj/mermaid-cli/pull/509)). Browserless notes that ported pixel-based loops "click in the wrong place" on Gemini because its coordinates are normalized ([Browserless](https://docs.browserless.io/ai-integrations/computer-use/gemini-computer-use)).
- I found **no public quantitative A/B** of "native CU tool versus a generic MCP CU tool" for any frontier model. cua's Bench v2 is set up to measure exactly this, but it has not published results yet ([cua-driver-bench](https://github.com/trycua/cua/tree/main/benchmarks/cua-driver-bench)).

Things that bite a model-agnostic server:

1. **Coordinates follow the image the model saw, not the one you sent.** "The coordinates Claude returns are pixel positions in the image Claude sees: your image after Claude resizes it" ([vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)). Claude Code may also scale MCP images down before the API sees them ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). An MCP server cannot detect either step. The fix is to send frames that no one will resize. 1372x887 is exactly 1568 visual tokens, the old-tier limit, which matches the size Claude Code's own CU uses for a 3456x2234 Retina capture ([Claude Code computer use](https://code.claude.com/docs/en/computer-use)).
2. **Claude pads to multiples of 28 px.** Normalize by the resized size, not the padded size ([vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)).
3. **Error results cannot carry images on Anthropic.** The API returns "all content must be type `text` if `is_error` is true" ([pi #10792](https://github.com/earendil-works/pi/issues/10792)). A failed script that already emitted a screenshot must either drop the image or not set `isError`.
4. **More than 20 images in one Claude request** tightens every image to 2000 px per side, including old screenshots in history ([Claude vision](https://platform.claude.com/docs/en/build-with-claude/vision)). Long sessions need small frames or pruning.
5. **Pruning breaks caches and, on Claude 5.5-era models, thinking.** Anthropic says to avoid client-side screenshot pruning on Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 and use server-side tool result clearing instead ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). An MCP server does not control history, so it should send fewer, smaller images.
6. **OpenAI-compatible chat completions cannot put images in `role:"tool"` messages.** Harnesses work around it by lifting images into a user message, which loses the link to the call ([OpenCode #52977](https://github.com/anomalyco/opencode/issues/52977)). This matters most for open-weight models served through vLLM or OpenRouter.

### 3. MCP spec features relevant to CU (revision 2026-07-28)

The current revision is 2026-07-28 ([spec](https://modelcontextprotocol.io/specification/latest), [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). What changed and what it means for us:

- **Stateless core.** No `initialize` handshake, no `Mcp-Session-Id`. Each request carries protocol version and client capabilities in `_meta`. Servers must implement `server/discover`. "Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments" ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). A persistent REPL over stdio is fine because one process serves one client. Over HTTP, the REPL needs a session handle argument.
- **Multi round-trip requests replace server-to-client requests.** A tool call can return `resultType:"input_required"` with `inputRequests` (for example `elicitation/create`). The client retries the call with `inputResponses` and `requestState` ([tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). For approvals, this means the engine pauses before acting, returns `input_required`, and does the action on the retry. It also means the approval prompt and the action are tied to the same tool call, which is nice.
- **Elicitation.** Form mode for structured data, URL mode for flows that must not pass through the client. Servers "MUST NOT" use form mode for passwords, API keys, tokens or payment data ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). URL-mode `notifications/elicitation/complete` and `elicitationId` were removed.
- **Deprecated:** roots, sampling and logging. Sampling's suggested replacement is "integrate directly with LLM provider APIs" ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). An MCP CU server cannot borrow the host's model for grounding. If we want a helper grounding model, the engine calls it directly.
- **Tasks** moved to an extension with polling via `tasks/get` and `tasks/update` ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)). Among the harnesses in this note, only VS Code Copilot and GitHub Copilot CLI were recorded as supporting tasks (2025-11-25 era) in the last official client list. Codex's own code mode uses a simpler yield pattern instead: `yield_time_ms` plus a `wait` tool with a cell ID ([Codex code-mode source](https://github.com/openai/codex/blob/main/codex-rs/code-mode-protocol/src/description.rs)).
- **Tool results** can mix text, image, audio, resource links and embedded resources, each with `audience` and `priority` annotations. `structuredContent` plus `outputSchema` is optional, and servers "SHOULD also return the serialized JSON in a TextContent block". Tool execution errors use `isError:true` and should go to the model for self-correction ([tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).
- **Deterministic tool order** is now a SHOULD, to help client and LLM prompt caching. List results carry `ttlMs` and `cacheScope` ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- **Extensions:** MCP Apps (inline HTML UI, supported by Claude web and Desktop, VS Code, ChatGPT, Cursor, Goose and others), Skills over MCP, auth extensions ([extension matrix](https://modelcontextprotocol.io/extensions/client-matrix)). MCP Apps could host a live view and takeover button in those clients later. Not needed for v1.
- **Security text in the spec:** clients SHOULD prompt for confirmation on sensitive operations, show tool inputs, apply timeouts and "Log tool usage for audit purposes". Servers MUST validate inputs, enforce access controls, rate limit and sanitize outputs ([tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).
- The official client feature list (`docs/clients.mdx`) was deleted from the spec repo on 2026-05-27. Its last version is still in git history (commit `87993a6` of `modelcontextprotocol/modelcontextprotocol`), and I used it only as a dated cross-check. It recorded Elicitation for Claude Code, Codex, Cursor, Goose and VS Code, and not for Gemini CLI, OpenCode, Zed or ChatGPT at that time.

### 5. Tool design: code mode, fine-grained tools, or both

Evidence for code mode:

- OpenAI recommends code execution for GPT-6 Astra CU and describes the benefit plainly: "One call can combine actions, loops, or conditional logic" ([computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use)).
- Anthropic's programmatic tool calling "improved performance by an average of 11% while using 24% fewer input tokens" on BrowseComp and DeepSearchQA ([programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). Anthropic's "code execution with MCP" post shows a 150,000 to 2,000 token drop (98.7%) from loading tool definitions on demand, and lists the costs: sandboxing, resource limits, monitoring ([Anthropic engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)).
- Cloudflare's argument is that models have seen far more real TypeScript than synthetic tool-call tokens. They give no numbers ("The results are striking") ([Cloudflare Code Mode](https://blog.cloudflare.com/code-mode/)).
- CodeAct: "up to 20% higher success rate" than JSON or text actions across 17 LLMs, ICML 2024 ([arXiv 2402.01030](https://arxiv.org/abs/2402.01030)).
- Harness adoption: Codex code mode, Pi codemode (default for MCP), Cloudflare Code Mode. cua-driver's benchmark arm runs with `run_script` on as the default ([cua-driver-bench](https://github.com/trycua/cua/tree/main/benchmarks/cua-driver-bench)).

Evidence for keeping fine-grained tools:

- Trained GUI specialists (UI-TARS, Qwen GUI agents, AutoGLM) emit action grammars, not code. There is no evidence they write good JS against a custom API (**unverified** either way).
- Anthropic and OpenAI native CU tools are fine-grained action schemas, and those are what their RL environments trained.
- Fine-grained tools give the harness per-action visibility and approval. A script hides many actions inside one call, so approval must move into the runtime.
- Some harnesses wrap MCP tools in their own code mode (Pi by default, Codex behind a flag). A `js` tool called from inside another code runtime is code mode inside code mode, and the outer script must forward images explicitly. Simple tools compose better there.

Latency and token notes:

- Most CU latency is model round trips. Batching attacks that directly: Anthropic batch actions, OpenAI `actions[]`, Gemini parallel calls, and code mode. A fine-grained MCP profile gets batching only if the harness emits parallel tool calls, and harnesses may run parallel calls concurrently. The engine must serialize actions per session regardless of what the harness does.
- Accessibility-tree text with element indices is cheaper than pixels and does not depend on image scaling. browser-use keeps index-only clicking by default and turns on coordinate clicking only for models it trusts (Claude Sonnet 4.5, Opus 4.5, Fable 5, Gemini 3 Pro, its own models) ([browser-use tools/service.py](https://github.com/browser-use/browser-use/blob/main/browser_use/tools/service.py)).

Security of letting the model run code:

- If the REPL is a plain Node process, model-written code can `require('child_process')`, read files and open sockets. That escapes the harness's own shell sandbox and approval rules. Codex CU is a trusted first-party binary; an open project cannot assume that. I did not verify how Codex CU's `cua_repl` restricts its Node runtime (**unverified**).
- Every comparable runtime removes ambient authority. Codex code mode: "no Node, no file system, no network access, no console". Cloudflare: V8 isolates where `fetch()` and `connect()` throw. Pi: QuickJS sandbox. OpenAI: "For generated code, enforce permissions in the exposed helpers and runtime; a single script can perform many actions" ([integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)).
- GUI terminals are a shell escape too. Codex CU refuses terminal apps and itself; Claude Code warns that terminals and IDEs are "Equivalent to shell access" and limits them to click-only ([Codex CU](https://developers.openai.com/codex/computer-use), [Claude Code CU](https://code.claude.com/docs/en/computer-use)).

### 6. Adapter architecture and prior art

- **trycua/cua agent SDK.** One loop module per model family, selected by model-name regex: `anthropic`, `openai`, `gemini`, `qwen3vl`, `qwen35`, `uitars`, `uitars2`, `glm45v`, `opencua`, `holo`, `gta1`, `internvl`, `moondream3`, `omniparser`, plus `composed_grounded`, which pairs a reasoning model with a grounding model through element descriptions ([loops](https://github.com/trycua/cua/tree/main/libs/python/agent/cua_agent/loops)). It routes through LiteLLM. This is the most complete public map of per-model action formats.
- **Cua Driver.** A background driver that "Speaks MCP over stdio" and "drives native macOS apps without stealing focus". MCP is "the runtime-neutral agent boundary"; app SDKs in Python and TypeScript sit on a C ABI. Permission modes `standard`, `bounded` (reviewed manifest) and `unrestricted` are fixed at process launch. Optional perception binds a pixel click to a one-use `capture_id` from the observation ([cua-driver README](https://github.com/trycua/cua/blob/main/libs/cua-driver/README.md)). It serves MCP 2026-07-28 over stdio and keeps the legacy `initialize` flow, ships its skill as embedded resources, and verified both paths with Codex 0.154.0 and Claude Code 2.1.268 ([mcp-protocol-and-skills.md](https://github.com/trycua/cua/blob/main/libs/cua-driver/docs/mcp-protocol-and-skills.md)). This is the closest prior art to what we want. It is worth a deeper look by whichever agent covers existing engines.
- **Cua Driver Bench v2.** Fixes the harness and model and swaps only the CU tool layer: Cua Driver, Codex CU ("Sky", via the `cua_repl` launcher registered in Claude Code as `codex-cu`), and Claude Desktop's CU helper behind a small adapter. It measures success and "background completion" (no focus steal, pointer move or keystroke loss). No results published yet ([README](https://github.com/trycua/cua/blob/main/benchmarks/cua-driver-bench/README.md)). We should reuse this method and maybe the task pack.
- **Vercel AI SDK.** Has provider-defined CU tools for all three labs: `anthropic.tools.computerToolset_20260801` (maps each member call back to one `action` field so `execute` sees the old shape), `openai.tools.computer`, and `google.computer_use` on the Interactions API ([AI SDK Anthropic](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic), [AI SDK OpenAI](https://ai-sdk.dev/providers/ai-sdk-providers/openai), [AI SDK Google](https://ai-sdk.dev/providers/ai-sdk-providers/google-generative-ai); details via search, spot-checked only). Its pattern of "native declaration, shared execute callback" is the right adapter shape.
- **LiteLLM.** Passes Anthropic CU tools through to Anthropic, Bedrock and Vertex and OpenAI's preview tool to OpenAI, with `supports_computer_use()` per model. Cross-provider translation drops what the target cannot express ([LiteLLM computer use](https://docs.litellm.ai/docs/completion/computer_use), [native passthrough](https://docs.litellm.ai/docs/anthropic_unified/native_passthrough)). I found no evidence it translates one CU schema into another.
- **OpenRouter.** Has an Anthropic-compatible `/api/v1/messages` endpoint, but I found no docs confirming CU tool passthrough or images in tool results; its chat-completions tool messages are typed as strings (**unverified**, from search summaries).
- **browser-use.** Many provider clients in `browser_use/llm`, one action schema, index-first targeting with per-model coordinate gating ([browser-use](https://github.com/browser-use/browser-use)).
- **Anthropic SDK toolset classes** (beta, 2026-10-07) give Claude-native adapters with an approval callback ([release notes](https://platform.claude.com/docs/en/release-notes/overview)).

### 7. Safety in a model-agnostic setting

What each lab recommends:

- **Anthropic.** Dedicated VM or container with minimal privileges, no sensitive credentials, domain allowlists, human confirmation for consequential actions, and consent from end users. Tool results are scanned by injection classifiers ([computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Desktop products add per-app approval, a denied-apps list, some sensitive app categories blocked or limited by default, and a consumed global Esc ([Cowork CU](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork), [Claude Code CU](https://code.claude.com/docs/en/computer-use)).
- **OpenAI.** Isolated browser or VM with allow lists; "Treat screen content as untrusted"; confirm at the point of risk; bound and verify runs. The integration guide has concrete tiers. "Hand-off required" for the last step of a password change and for bypassing browser safety barriers. "Always confirm at action time" for deletes, permission changes, CAPTCHAs, installing software, sending or posting, financial transactions and system settings. "Pre-approval can be enough" for logins, uploads and file moves. For batches, stop before the first action that needs confirmation ([integration recipes](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)). Codex CU adds per-app "Always allow", refuses terminals, itself and admin prompts, and enterprise app rules where Block wins ([Codex CU](https://developers.openai.com/codex/computer-use)).
- **Google.** Model-side `safety_decision` with confirmation, optional injection detection, excluding risky functions, and custom handoff functions like `yield_to_user` ([Gemini computer use](https://ai.google.dev/gemini-api/docs/computer-use)).

What changes when the model is arbitrary:

- Model-side protections (Anthropic classifiers, Gemini `safety_decision`) exist only on the native API paths. Over MCP in a third-party harness, or with an open-weight model, the engine is the only layer that knows what is on screen and what is about to happen. Policy has to live in the engine.
- Elicitation is missing or broken in several harnesses (matrix above). A model can also try to "approve" itself if approval is just a tool argument. So approvals need a channel the model cannot write to. Elicitation where it works; otherwise a local OS prompt, tray menu or notification owned by the engine.
- Code mode multiplies the actions per model turn. Approval checks, app scoping and rate limits must run inside each `cua` method, not at the tool-call boundary.
- Audit: the MCP spec asks clients to log tool usage. The engine should log every action with app, target, frame ID and outcome. Cua Driver's opt-in "Computer History" stores only an allowlisted metadata set, encrypted and local, with no screenshots or typed text ([cua-driver README](https://github.com/trycua/cua/blob/main/libs/cua-driver/README.md)). That is a good privacy default.

## Implications for our project

### Recommended interface design

```
                 +--------------------- engine (one process per desktop) ---------------------+
                 |  observe: apps, windows, AX tree with element indices, frames (screenshots) |
                 |  act: click/type/key/scroll/drag by element index or frame point            |
                 |  policy: app approvals, blocklist, risk tiers, rate limits, kill switch     |
                 |  frames: capture -> crop -> resize to profile -> encode, frameId + scale    |
                 |  audit log, optional recording                                              |
                 +--------------^---------------------------^---------------------------^------+
                                |                           |                           |
     face 1: MCP server         |   face 2: native adapters |   face 3: frame/coord     |
     (stdio + HTTP, legacy and  |   for direct API agents   |   layer shared by all     |
      2026-07-28)               |                           |                           |
     profile "code": js,        |   anthropic toolset +     |   spaces: image_px,       |
       js_reset                 |     computer_20251124     |   norm1000, norm999,      |
     profile "tools": get_state,|   openai computer +       |   screen; frame freshness;|
       click, type, key, scroll,|     exec_js               |   no-rescale size per     |
       drag, zoom, list_apps    |   gemini computer_use     |   target model            |
                                |   qwen computer_use       |                           |
                                |   ui-tars grammar         |                           |
```

1. **One engine API, typed once.** Every face calls the same small set of operations. Targets are a union: `{ element: number, frameId }` or `{ x, y, frameId, space: "image_px" | "norm1000" | "norm999" }`. The engine maps everything to screen points through the frame's recorded scale. This is where Retina, window offsets and model-specific normalization live. It also rejects stale frames (window moved or closed), like Cua Driver's `capture_id` rule.
2. **MCP is the default front end.** Keep Codex CU compatibility for the code profile: `js` runs code in a persistent runtime with a `cua` object and an image emitter; `js_reset` clears it. Drop `turn_ended`, since other harnesses will never call it; use idle timeouts instead.
   - Run `js` in a capability sandbox (V8 isolate, `isolated-vm` or QuickJS) with no `require`, filesystem, network or process access. The only authority is the `cua` object. Measure the speed cost against plain Node before deciding (open question below).
   - Keep each `js` call under about 30 s. Codex's default MCP tool timeout is 60 s. For longer work, return early with a cell ID and add a `js_wait` style call, which is the Codex code-mode pattern, rather than depending on MCP Tasks.
   - Offer a "tools" profile with about 8 fine-grained tools for open-weight models, for Pi-style harnesses that wrap MCP in their own code mode, and for users who want per-action approval in the harness. Pick the profile with a flag, not by guessing from `clientInfo`, which Claude Desktop mislabels.
   - Every result is text first, then at most one image. Pair images with a text block that states frame ID and pixel size, for example "frame f12, 1372x887, click coordinates are pixels in this image". Add `_meta: {"codex/imageDetail":"original"}` on images. Never attach images to `isError:true` results.
   - Default frame size: the largest size with `ceil(w/28) * ceil(h/28) <= 1568` and long edge at most 1568. No Claude model or Claude Code will rescale it, and OpenAI cost stays near 1.2k to 1.6k tokens. Add a `zoom(region)` call for dense UI, like Anthropic's toolset, instead of raising the default.
   - Keep text output under 20 KB per call (Pi's truncation point) and well under Claude Code's 10,000-token warning. Return compact AX trees, filtered to the target window, with pagination.
   - Write server `instructions` so the first line stands alone and the first 512 characters explain the workflow. Codex and Pi read these; Claude Code shows them with tool search.
   - Serve both protocol eras: `initialize` for 2025-06-18/2025-11-25 clients and `server/discover` plus per-request `_meta` for 2026-07-28. Use MRTR `input_required` for approvals on modern clients and `elicitation/create` on legacy ones.
3. **Native adapters for direct API use.** Each adapter has four typed parts: the tool declaration, a parser from provider calls to engine actions, a formatter from engine results to provider results, and an image policy (size, format, detail flag). Batch semantics belong to the adapter: in order, stop on first failure, answer every call, and attach a final screenshot. Specific rules:
   - Anthropic toolset: frames within 2576 px and 4784 tokens on new models, return `toolset_name`, use the exact "Not executed" text after a failure, and keep `computer_20251124` for Bedrock and Opus 4.5 to 4.7.
   - OpenAI: `detail:"original"`, 1440x900 or 1600x900, and an `exec_js` adapter that reuses the MCP code runtime for GPT-6 Astra, since OpenAI recommends that path.
   - Gemini: `environment:"desktop"`, normalized coordinates, `ultra_high` media resolution, map `safety_decision` onto engine policy, preserve thought signatures, and add a `yield_to_user` custom function.
   - Qwen and UI-TARS: port the request formats from cua's loops. Lift images into user messages when the serving stack cannot carry them in tool messages.
4. **Element indices first, pixels second.** Index targeting is the only path that is exact for every model, every harness, and every image scaling. It is also what makes Codex CU fast. Pixel clicks stay available, with normalized spaces for Gemini, Qwen and GLM.
5. **Policy lives in the engine.** Per-app approval with session and "always" scopes, a default blocklist (terminals, our own process, password managers, OS security prompts), risk tiers modeled on OpenAI's list, a consumed global kill key, pause when the real user types or moves the pointer, and an action log. Elicitation is one way to show the prompt, not the policy itself.
6. **Measure like Cua Driver Bench.** Same harness and model, swap only the tool layer. Arms: our MCP code profile, our tools profile, Codex CU over MCP, and native adapters on direct APIs. Track success, turns, wall time, tokens, and background completion. Save every run's frames and action log so results can be inspected later.

### What this buys "near-native" performance

- Frontier models in harnesses get Codex-style code mode, AX-first targeting and frames that no one rescales. That is the setup already shown to work under Claude Code.
- Frontier models on direct APIs get their trained schema through thin adapters on the same engine.
- Open-weight models get their trained action format and coordinate space through adapters, or the simple tools profile in harnesses.

1. How much accuracy does Claude or GPT lose with a generic MCP CU tool versus its native toolset? No public numbers exist. Cua Bench v2 may publish them; otherwise we run our own A/B.
2. Exactly when does Claude Code rescale an MCP image, and does the API resize further? Test with frames just inside and just outside the 1568-token box and check click error.
3. What sandbox gives Codex-level REPL speed: `isolated-vm`, QuickJS, Deno with no permissions, or a separate locked-down Node process? Measure cold start and per-call overhead.
4. How reliable are MRTR approvals in practice? Claude Code v2, VS Code and ChatGPT are the first clients to test. Cowork is known to drop them today.
5. Should the code profile also expose fine-grained tools at the same time? It costs context and splits model behavior. Test both.
6. Do Gemini and Qwen in their own CLIs (Gemini CLI, Qwen Code) click accurately with pixel coordinates in our frames, or do they need `norm1000` exposed as the default for them?
7. How do Pi's codemode and Codex's code mode handle our `js` tool's images when they wrap it? Pi needs `image()` forwarding; Codex code mode is still off by default.
8. ChatGPT needs a tunnel to reach a local desktop server, and image visibility varies by account. Is ChatGPT worth supporting in v1?
9. Is Codex CU's `cua_repl` Node runtime restricted in any way? That affects how closely we should copy its API surface without copying its trust model.
